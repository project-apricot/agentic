# Agentic

A tool an AI agent can call is two things at once: an operation, and a prompt. The operation
belongs beside the code that implements it. The prompt — the name, the description a model selects
on, the shape it fills in — belongs there too, because a declaration kept anywhere else drifts
from the thing it describes.

What does *not* belong there is how the tool is reached, or what a caller must hold to reach it.
Those are the host's, and this library is built so it never has to learn either.

## Packages

| Package | What it is |
| --- | --- |
| `ApricotFramework.Agentic.Tools` | The tool abstraction, schema generation, the registry and the invoker |
| `ApricotFramework.Agentic.Tools.AspNetCore` | Registration, and authorization read from the attributes a tool declares |

## Two things it refuses to know

**How a tool is reached.** Being local or remote is a property of the caller. An in-process agent
loop and a remote protocol such as MCP are two callers of one declaration, so nothing in the tool
mentions either. A host that wants tools over gRPC, HTTP or a message queue writes that transport
once and every tool is reachable through it.

**What a permission is.** Where permissions live, how they are named, and what decides them are
answered by the application already. `IAgentToolFilter` is the whole of what this library knows
about the subject — one method, answering allow or deny — and the ASP.NET Core package implements
one by reading the authorization attributes a tool declares and handing them to the host's own
pipeline.

## Install

```bash
dotnet add package ApricotFramework.Agentic.Tools
dotnet add package ApricotFramework.Agentic.Tools.AspNetCore
```

## Status

Preview. The shape is still moving and breaking changes should be expected until 1.0. Two have
already happened in design: authorization moved from a property on the tool to an attribute, and
results moved from a single value to a sequence. Both would have been major bumps.
